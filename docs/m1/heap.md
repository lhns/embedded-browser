# M1 heap gate: Wikipedia-scale page

The committed pages peak at 1.4-3.9 MB. The only page near the 12 MB P4 cap was a fetched Wikipedia article (10.5 MB in docs/m0/host-results.md), which is not committed. `testpages/bigpage.html` is a synthetic stand-in that CI can run.

- **Generated by** `testpages/generate.py`: a 200 KB stylesheet (about 2000 rules over 900 classes), infoboxes with images, tables, floats, lists, and six embedded 300x250 PNGs (1.8 MB decoded). All text and pixels are generated.
- **Fits the limits** in `Limits::default()`: 0.65 MB file (limit 2 MB), 2.5 k DOM nodes, and the stylesheet is inline.
- **Measured** with `measure heap-cap --wasm target/wasm32-wasip1/release/measure.wasm --cap-mb 12`, the CI heap-cap command:

| page | peak MB (wasm32-wasip1, core API, 32px bands) | P4 gate (12 MB) | S3 tier (4 MB) |
|---|---|---|---|
| bigpage | 11.45 | pass | over |

- **Margin:** 0.55 MB. The gate does not count allocator overhead (about 0.4-0.8 MB for a page this size on ESP-IDF), so on a device this page would be at or past the cap. That is the margin problem the page is meant to expose; the cap was not raised.
- **Heap per node:** this page reaches Wikipedia's heap with 2.5 k nodes instead of 6 k. The heap is driven by the number of text blocks (paragraphs, list items, table cells) and by stylesheet size, not by node count alone: each `li` or `p` with text costs about 2.5-5 KB (64-bit), and the 200 KB stylesheet about 3.7 MB. Pages with many short text blocks can therefore exceed the cap sooner than their node count suggests.
- **Golden:** `testpages/golden/bigpage.png` (first screen only). No Chromium reference.
